\section{Database Management Systems}
\label{sec:bg-dbms}

Database Management Systems (DBMS) are based on a \textit{data model}, which abstractly describes how data is organized. Most widely-used DBMS are based on the \textit{relational data model} proposed by Codd, where data is organized into tables consisting of rows and columns. Structured Query Language (SQL) is the most commonly used language in relational DBMS to create databases, tables, insert rows, as well as manipulate and retrieve data \cite{sqlite}.

SQL is a declarative language: the user specifies \textit{what} data to retrieve or modify, not \textit{how} to execute the operation. A DBMS processes a SQL statement through several internal stages. First, the \textit{tokenizer} breaks the raw SQL text into lexical tokens (keywords, identifiers, literals, operators). The \textit{parser} then consumes these tokens and constructs an abstract syntax tree (AST) that represents the statement's syntactic structure. The \textit{query optimizer} analyzes the AST and selects an efficient execution plan, choosing join orders, index usage, and access methods. Finally, the \textit{execution engine} carries out the plan against the stored data and returns results.

SQLite is the most widely deployed database engine in the world. Unlike client-server systems such as PostgreSQL or MySQL, SQLite operates as a self-contained, serverless library embedded directly into the host application. It is written in approximately 150,000 lines of C code and is deployed in every major smartphone operating system, web browser, and the Python standard library, with an estimated three trillion active installations \cite{sqlite}. SQLite's execution engine, called the Virtual Database Engine (VDBE), compiles SQL statements into bytecode programs that operate on B-tree page structures. Key subsystems include the query planner, the window function engine, the Full-Text Search (FTS3/FTS5) virtual table module, and the generated column processor. Vulnerabilities in these deep subsystems --- integer overflows in expression evaluation, use-after-free in window function processing, null pointer dereferences in column resolution --- require specific SQL structural patterns to trigger, making them difficult to discover through random testing alone.


\section{Context-Free Grammars}
\label{sec:bg-cfg}

Applications that process highly structured input, such as SQL, cannot be effectively tested by conventional mutation-based methods that operate on raw bytes. Context-Free Grammars (CFGs) provide a formal mechanism to specify the structure of such input languages, enabling the systematic generation of syntactically valid inputs.

A context-free grammar is formally defined as a tuple $G = (N, \Sigma, P, S)$ where $N$ is a finite set of non-terminal symbols, $\Sigma$ is a finite set of terminal symbols disjoint from $N$, $P \subseteq N \times (N \cup \Sigma)^*$ is a finite set of production rules, and $S \in N$ is the start symbol. Each production rule has the form $A \to \alpha$ where $A \in N$ is a single non-terminal and $\alpha \in (N \cup \Sigma)^*$ is a sequence of terminals and non-terminals. Since the left-hand side of each rule consists of exactly one non-terminal, the possible derivations depend only on that non-terminal and no surrounding context --- hence the name \textit{context free}.

To generate a string from a grammar, a matching production rule is applied to the start symbol $S$. As long as the resulting sequence contains non-terminals, another rule is selected and applied to one of them. This process continues until only terminal symbols remain. Each string generated by a CFG can be represented by its \textit{derivation tree}: the root is labelled with $S$, each internal node is labelled with a non-terminal, and the children of each node correspond to the right-hand side of the production rule applied at that node. Leaf nodes are labelled with terminal symbols. The generated string is obtained by reading the leaf nodes left to right, a process called \textit{unparsing}.

For SQL-based fuzzing, a grammar can be designed so that its non-terminals correspond to SQL syntactic categories and its terminals correspond to SQL keywords, operators, and literals. Consider the following grammar fragment that generates simple SQL queries:

\begin{lstlisting}[language=Python, caption={A grammar fragment for SQL in the Nautilus Python DSL. Non-terminals are enclosed in curly braces. Each \texttt{ctx.rule} call defines one production rule.}, label={lst:sql-grammar}]
ctx.rule("Stmt", "SELECT {Expr} FROM {Table}")
ctx.rule("Stmt", "{Stmt}; {Stmt}")
ctx.rule("Expr", "{Col}")
ctx.rule("Expr", "{Func}({Expr})")
ctx.rule("Table", "t1")
ctx.rule("Func", "coalesce")
ctx.rule("Func", "printf")
ctx.rule("Col", "c1")
\end{lstlisting}

In Listing~\ref{lst:sql-grammar}, the non-terminal \texttt{Stmt} can derive either a single \texttt{SELECT} query or a semicolon-separated sequence of statements (enabling multi-statement inputs). The non-terminal \texttt{Expr} can derive either a column reference or a function call wrapping another expression, providing recursive structure. Starting from \texttt{Stmt}, one possible derivation produces:

\begin{center}
\texttt{Stmt} $\to$ \texttt{SELECT \{Expr\} FROM \{Table\}} $\to$ \texttt{SELECT \{Func\}(\{Expr\}) FROM t1} $\to$ \texttt{SELECT printf(\{Expr\}) FROM t1} $\to$ \texttt{SELECT printf(c1) FROM t1}
\end{center}

Figure~\ref{fig:derivation-tree} shows the corresponding derivation tree. Each internal node is labelled with a non-terminal, and its children correspond to the symbols on the right-hand side of the production rule applied at that node. Leaf nodes carry terminal symbols. Reading the leaves left to right produces the generated string \texttt{SELECT printf(c1) FROM t1}.

The key property is that every string derivable from this grammar is a syntactically valid SQL fragment. By designing the grammar to cover relevant SQL constructs --- window functions, generated columns, subqueries, set operations --- the generation process is guaranteed to produce inputs that pass the DBMS parser and reach the deeper query planning and execution stages where vulnerabilities reside.

Once a derivation tree exists, \textit{tree-level mutations} can generate new inputs while preserving syntactic validity. Three fundamental mutations are commonly employed:

\begin{itemize}
    \item \textbf{Random mutation:} select a non-terminal node in an existing tree and replace the entire subtree rooted at that node with a freshly generated subtree for the same non-terminal.
    \item \textbf{Random recursion:} identify a recursive non-terminal (one that can derive itself) and either expand it by adding recursion levels or collapse it by replacing the subtree with a base case.
    \item \textbf{Splice mutation:} select two trees from the corpus, find nodes with the same non-terminal label, and swap the subtrees rooted at those nodes between the two trees.
\end{itemize}

These mutations operate on the tree structure rather than raw bytes, so every mutated tree still corresponds to a valid derivation and produces a syntactically correct string when unparsed. This property is critical for fuzzing targets like SQL engines, where byte-level mutations overwhelmingly produce parser-rejected inputs.


\section{Fuzzing}
\label{sec:bg-fuzzing}

Fuzzing is an automated software testing technique that generates a large number of inputs, feeds them to a program under test, and monitors for anomalous behavior such as crashes, hangs, or sanitizer violations \cite{fuzzingsurvey}. The technique is particularly effective at finding inputs with \textit{unexpected characteristics} that trigger vulnerabilities --- precisely the kind of inputs that human-written tests tend to miss.

Fuzzers can be classified along two axes. Along the \textit{analysis} axis: \textit{black-box} fuzzers generate inputs with no knowledge of the program's internals; \textit{white-box} fuzzers use heavyweight techniques such as symbolic execution to reason about program paths; \textit{greybox} fuzzers use lightweight instrumentation (typically branch coverage) to observe execution without full symbolic analysis \cite{fuzzingsurvey}. Along the \textit{generation} axis: \textit{mutation-based} fuzzers start from a seed corpus and apply random modifications (bit flips, byte insertions, splicing); \textit{generation-based} fuzzers construct inputs from scratch according to a model such as a grammar. Figure~\ref{fig:fuzzing-taxonomy} positions representative tools along these two axes.

Coverage-guided greybox fuzzing, pioneered by AFL \cite{afl}, is the dominant paradigm in modern fuzzing. The target program is compiled with instrumentation that records which code edges (basic block transitions) are exercised during execution. The coverage information is stored in a shared memory bitmap, typically 64KB to 2MB, where each byte corresponds to a hashed edge. After executing a test input, the fuzzer checks whether the input exercised any previously unseen edges. If so, the input is retained in the corpus for further mutation; otherwise it is discarded. This feedback loop transforms fuzzing from random input generation into a directed search that progressively explores deeper program logic.

The AFL fork server model provides an efficient execution mechanism. Rather than creating a new process for each test input, the fork server loads the target program once into a parent process, then creates child processes via \texttt{fork()} for each test case. The child inherits the initialized program state, executes the input, and exits. The parent collects the exit status and coverage bitmap, then forks the next child. This amortizes initialization overhead across all executions, typically improving throughput by an order of magnitude. The fork server also isolates crashes: when a child triggers a segmentation fault or sanitizer violation, the parent remains unaffected.

General-purpose fuzzers such as AFL and libFuzzer \cite{libfuzzer} are highly effective for binary file formats and network protocols. However, they struggle with highly structured inputs like SQL. Random byte-level mutations on a SQL string overwhelmingly produce inputs that are rejected by the parser's syntax check, never reaching the deeper query optimizer, window function engine, or virtual table logic where vulnerabilities reside. Grammar-based fuzzing, as described in Section~\ref{sec:bg-cfg}, addresses this barrier by generating inputs from a context-free grammar. Combining grammar-based generation with coverage-guided feedback yields a \textit{grammar-based greybox fuzzer} --- a system that generates syntactically valid inputs and uses coverage feedback to steer generation toward unexplored program regions. Nautilus \cite{nautilus} is the first system to implement this combination, maintaining a corpus of derivation trees rather than flat strings, and applying tree-level mutations guided by edge coverage. Nautilus discovered 49 previously unknown bugs across mruby, PHP, ChakraCore, and Lua interpreters, demonstrating that grammar-based greybox fuzzing significantly outperforms both pure grammar fuzzers (no feedback) and pure mutation fuzzers (no grammar) on structured-input targets.


\section{Related Work}
\label{sec:bg-related}

Several lines of research address the challenge of testing software that processes structured inputs. This section reviews the most relevant approaches and positions DBMS-Nautilus relative to each.

Mutation-based greybox fuzzers, exemplified by AFL~\cite{afl}, apply random byte-level transformations --- bit flips, arithmetic increments, block insertions --- to a seed corpus and retain inputs that discover new coverage. AFL's simplicity and speed have made it the dominant fuzzing tool for binary file formats, network protocols, and media parsers. However, its mutations operate on the raw byte representation of the input, with no awareness of the underlying grammar. When applied to highly structured languages like SQL, the overwhelming majority of mutated inputs are rejected by the parser's syntax check before reaching deeper program logic. Greybox fuzzers that attempt to mitigate this limitation through taint-guided mutation or symbolic-execution-assisted input generation improve parser pass-through rates but still lack the ability to systematically construct inputs that exercise specific syntactic categories.

Generation-based fuzzers construct inputs from a formal specification rather than mutating existing ones. CSmith~\cite{csmith} generates random C programs according to the C language grammar, specifically targeting undefined behavior in C compilers. CSmith demonstrates that grammar-driven generation can discover deep compiler bugs that no mutation-based tool has found, but it operates without coverage feedback: each generated program is independent of all previous executions, with no mechanism to steer generation toward unexplored code paths. LangFuzz~\cite{langfuzz} combines grammar-based generation with corpus-derived code fragments to fuzz JavaScript interpreters. By parsing existing JavaScript programs and recombining fragments according to the language grammar, LangFuzz generates inputs that are both syntactically valid and semantically plausible. However, LangFuzz requires a pre-existing corpus of real programs and does not use coverage feedback. IFuzzer~\cite{ifuzzer} applies genetic programming to evolve JavaScript programs that maximize code coverage, but its fitness function is evaluated per-generation rather than per-input, limiting its responsiveness to coverage signals. Skyfire~\cite{skyfire} learns a probabilistic context-sensitive grammar from a corpus of seed inputs and uses it to generate diverse seeds for downstream fuzzers. While Skyfire's learned distributions capture corpus-level patterns, it serves as a seed generator rather than a standalone fuzzer and does not maintain a feedback loop during fuzzing.

Testing tools specifically targeting database management systems have pursued several distinct strategies. SQLsmith~\cite{sqlsmith} generates random SQL queries by introspecting the schema of an existing database, using the catalog metadata to construct type-correct queries with valid table and column references. This schema-aware approach produces queries with high semantic validity, but SQLsmith operates without coverage feedback and without grammar weights --- it samples uniformly from its query templates, with no mechanism to bias generation toward vulnerability-relevant constructs. Squirrel~\cite{squirrel} introduces an intermediate representation (IR) for SQL that enables type-aware mutations. By parsing SQL into an IR that encodes semantic relationships (such as which columns belong to which tables), Squirrel can mutate queries while preserving semantic validity. However, Squirrel requires a custom IR parser for each SQL dialect and does not support weighted sampling over structural patterns. SQLancer~\cite{sqlancer} takes a fundamentally different approach: rather than searching for crashes, it generates queries and checks whether the DBMS returns correct results. NoREC~\cite{norec} and TLP~\cite{tlp} extend this differential testing methodology --- NoREC compares optimized and unoptimized query execution, while TLP decomposes queries into partitioned variants and checks result equivalence. These tools are highly effective at detecting logic bugs (incorrect query results) but do not target memory safety violations or undefined behavior, which require a crash-based oracle.

Nautilus~\cite{nautilus} is the first fuzzer to combine grammar-based input generation with coverage-guided feedback in a closed loop. It maintains derivation trees as its internal representation, applies tree-level mutations (random subtree replacement, recursive expansion, and splicing between trees), and retains inputs that discover new coverage edges. Nautilus discovered 49 bugs across four interpreter targets and demonstrated that the combination of grammar and feedback significantly outperforms either approach alone. However, Nautilus uses a general-purpose grammar with uniform sampling --- all production rules have equal probability, with no mechanism to bias generation toward structural patterns associated with specific vulnerability classes.

DBMS-Nautilus extends the Nautilus architecture with three domain-specific enhancements. First, the grammar is designed around structural primitives extracted from CVE root-cause analysis, encoding the SQL constructs that are known to stress vulnerability-prone code paths. Second, production rules carry numeric weights that bias sampling toward vulnerability-relevant constructs, allowing the grammar designer to concentrate fuzzing effort on the most productive regions of the input space. Third, the grammar generates self-contained SQL programs from an empty database, eliminating the need for a pre-populated schema or external database state.
